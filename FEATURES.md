# BAGEL — Feature History

Detailed version-by-version release notes, including the design rationale behind each feature. The [main README](README.md) keeps a condensed feature summary; this file is for "what changed in vX.Y and why."

---

## v1.3.1: MESH_RESOURCE + TRIANGLE_LIST Markers

Everything in v1.3.0, plus:

- **`visualization_msgs/Marker` type 10 (`MESH_RESOURCE`) now renders real meshes.** Drop a bag whose planner / perception stack publishes mesh markers (`nav2`, `moveit2`, the various `*_visualization` packages) and the pink-wireframe placeholder from v0.8 finally retires for any URI the user has wired up a package mapping for. The factory plumbs straight into the v1.3.0 `meshLoader` and `packageResolver` so the same `package://` mappings that animate a URDF also resolve marker meshes - one drag-and-drop per package, one set of URL prefixes persisted in `localStorage`, both consumers benefit. Lifecycle: the placeholder is in the scene immediately on `createMarkerObject`; the first `update(m)` with a non-empty `marker.mesh_resource` kicks off `loadMesh(uri)`; on resolve the loaded mesh swaps in for the placeholder and the placeholder is parented-but-hidden so dispose stays cheap; on rejection the placeholder stays visible and a single `console.warn` surfaces the URI plus the resolver's reason ("No mapping for package …" / "Unsupported file extension …" / Collada parser errors). The pink-wireframe failure mode from v0.8 is preserved, but it's now the failure mode rather than the only mode.
- **`mesh_use_embedded_materials` is honoured.** When the boolean field is `false` (the .msg default - matches RViz's "make the mesh the marker's colour" expectation), every Mesh material under the loaded subtree is cloned and re-tinted to `marker.color`. When `true`, the artist's baked-in materials from `.dae` / `.obj` carry through unchanged, except that `marker.color.a < 1` still applies an opacity overlay so debug overlays remain translucent without losing the underlying surface tone. Cloning before mutation is load-bearing - `meshLoader`'s LRU hands every consumer a shared-reference clone (geometries + materials), so two markers using the same URI with different colours would otherwise fight over a single material instance. The marker-side clone is the only safe place to apply the tint because the cache doesn't know about the marker's per-instance colour.
- **Stale-load guard.** A generation counter bumps on every URI change so a slow first-load that resolves *after* the user / publisher has switched the marker to a different mesh discards its result instead of yanking the wrong mesh into the scene. Same pattern the v0.4 single-flight playhead-driven hooks use, applied here at the per-marker level.
- **`visualization_msgs/Marker` type 11 (`TRIANGLE_LIST`)** renders `marker.points[]` as a Lambert-lit triangle soup, three vertices at a time. Per-vertex colours from `marker.colors[]` when its length matches `points.length` (planner cost surfaces, semantically-coloured convex hulls); otherwise the whole mesh inherits `marker.color`. Material is `MeshLambertMaterial` with `vertexColors: true` so the per-vertex colour path is just a different attribute upload - no material churn on each tick. `DoubleSide` shading because triangle-soup markers are routinely camera-flipped relative to the publisher's vertex order (the spec doesn't pin a winding convention); single-side culling would silently disappear chunks of the surface depending on view angle. Marker scale applies as a geometry multiplier the same way it does for primitives, which matches RViz so debug bags rendered side-by-side line up. An odd trailing vertex pair is dropped at ingest time so a half-published `points[]` doesn't draw a dangling sliver; fewer than three points hides the mesh entirely rather than crashing the `setAttribute` call.
- **Disposal stays cache-safe.** Marker disposal frees only the placeholder's geometry and material - the loaded mesh's geometries and materials are owned by `meshLoader`'s LRU and would corrupt the cache if disposed twice. Same convention `robotModel.ts` uses for URDF visuals: own what you allocated, let the loader own what it loaded.
- **12 new tests in `tests/components/markerObjects.test.ts`**, covering: placeholder-while-in-flight, swap-in-with-tint on resolve, persistent placeholder + single warn on rejection, embedded-materials passthrough, stale-load discard across URI change, vertex-coloured triangles, solid-colour fallback when `colors[]` is empty, orphaned-vertex truncation, fewer-than-three-points hide path, RViz-equivalent scale multiplication, mixed `CUBE + MESH_RESOURCE + TRIANGLE_LIST` independence, and `mesh_use_embedded_materials` default-false normalisation. Suite goes from 223 to 235 passing tests (246 collected, 11 still skipped behind the 10 GB ROS1 bag fixture); wall time stays under 19 s. `loadMesh` is mocked at the module boundary with `vi.hoisted` + `vi.mock` so the marker tests stay dependency-free and run alongside the rest of the suite without fetching anything.

Explicitly still out of scope (matches the v0.8 / v1.3.0 deferrals):
- **Collada texture-dependency resolution.** Some `.dae` files reference texture image files via relative paths; the package resolver flow handles top-level mesh files but not their texture dependencies. Mesh loads succeed but textures may 404; the failure surfaces as a `console.warn` from `THREE.TextureLoader` rather than the marker visibly breaking. Full texture-resolver flow stays a v1.3.3 / on-demand follow-up.
- **`mesh_resource_marker.mesh_use_embedded_materials = true` for STL meshes.** STL doesn't carry materials - it's raw triangles. When `mesh_use_embedded_materials=true` is set on a marker whose URI is an `.stl`, the loader's synthetic Lambert wrapper is whatever `meshLoader` chose (currently `0xcccccc`). This is a publisher-side bug (STL with embedded materials is nonsense), not something v1.3.1 tries to paper over.

## v1.3.0: URDF Robot Model in the 3D Scene

Everything in v1.2, plus:

- **Drop a URDF, watch the robot animate in every 3D panel.** A new `Robot` button in the toolbar opens a `UrdfLoadModal` where the user drops a `.urdf` (or pastes one as text) and BAGEL parses the model, surfaces any unbound `package://` references, and once every reference resolves, builds a Three.js subtree per open 3D panel anchored to the URDF's root link in world space. The bag's `/tf` stream places the anchor link in the world frame on every playhead tick; the panel's existing TF-resolved world transform is reused, so the robot rides with the bag's trajectory without the panel having to know about URDF at all. Joint states from `sensor_msgs/JointState` (auto-detected on the bag, conventionally `/joint_states`) animate revolute and prismatic joints; fixed joints and the absence of joint states render the model at its URDF rest pose. The Display card grows a per-panel `robot model` toggle so you can hide the model on a panel that's otherwise reading a tight point cloud without affecting siblings. This is the v1.3 banner feature - the v1.1 / v1.2 banner was "replace one CLI workflow"; v1.3 pivots to "make BAGEL feel like a real robotics tool, not just a bag viewer."
- **Zero-dependency URDF XML parser** (`src/parsers/urdf.ts`, ~600 LOC). URDFs are a constrained subset of XML so we hand-rolled a tiny recursive-descent tokenizer rather than pulling `@xmldom/xmldom` as a runtime dep or scoping `jsdom` to one test file. Handles elements with attributes (single + double quote forms), the five core entity refs (`&amp; &lt; &gt; &quot; &apos;` plus numeric `&#xNN; / &#NN;`), self-closing tags, comments, processing instructions, CDATA-as-text, and a token-counting DOCTYPE skip so bags exported from `xacro --inorder` (which prepend a DOCTYPE) still parse. Surfaces a typed `UrdfModel` with `links: Map<name, UrdfLink>`, `joints: Map<name, UrdfJoint>`, root-link discovery, distinct mesh URIs, and a structured warning list (`xacro`, `unknown-element`, `missing-link`, `missing-attribute`, `duplicate-name`, `malformed`). Geometry primitives (box / cylinder / sphere) parse with their defaults from the URDF spec; `<mesh>` carries `filename` + `scale` straight through to the loader. Joint types `fixed / revolute / prismatic / continuous / floating / planar` are surfaced; `<axis>` defaults to `(1, 0, 0)` per the spec; `<limit>` is parsed when present; `<mimic joint="…" multiplier="…" offset="…"/>` is captured so derived-joint groups (gripper fingers, wheel parallel linkages) animate correctly. Named-material references at the top level resolve into the link visuals during parse so the renderer doesn't have to walk a second registry. **Xacro detection is a hard error**: any `<xacro:…>` element or `${…}` substitution surfaces a specific message telling the user to pre-process with `xacro your.urdf.xacro > your.urdf` first. A pure-JS xacro evaluator is its own ~1000 LOC project and is explicitly out of scope.
- **Package resolver with localStorage persistence** (`src/parsers/packageResolver.ts`, ~280 LOC). URDFs reference meshes by ROS `package://<name>/<path>` convention rather than by URL, so BAGEL can't auto-resolve them - it has no ROS distro to look in, and walking GitHub raw URLs would be both fragile and a security risk. The resolver lets the user tell BAGEL where each referenced `<pkg>/meshes/` directory lives, *once* per package, persisted across sessions. Two binding kinds per package: **`file`** (drag-dropped folder; the modal uses a `<input type="file" webkitdirectory>` to capture the whole tree as `File` handles indexed by relative path, lookup falls back to suffix and basename matching when the drop root differs from the URDF's expected layout) and **`url`** (pasted URL prefix; everything after the package boundary appends to it for each mesh fetch). URL bindings survive a reload via `localStorage` under `bagel:package-roots:v1`; file bindings re-prompt on the next session but the modal remembers the package name with a "you mapped this last session" hint. `file://` URIs are rejected with a specific error (the browser can't fetch them from a non-file origin); `http://` / `https://` URIs pass through unchanged; bare paths are treated as relative URLs (useful for dev-time fixtures served from `/public`). The resolver exposes a subscribe API so the modal's "missing packages" list refreshes immediately after each binding is added without needing a remount.
- **Three.js mesh loader with lazy imports + LRU cache** (`src/utils/meshLoader.ts`, ~210 LOC). One entry point: `loadMesh(uri)` → `THREE.Object3D`. The loader for the file extension (`.stl`, `.dae`, `.obj`) is dynamically imported on first use so the main bundle stays slim for users whose URDFs are primitives-only. STL geometries get wrapped in a synthetic `MeshLambertMaterial` (Three.js's STL loader returns a `BufferGeometry`, not a `Mesh`); Collada and OBJ keep whatever materials the artist baked into the file. Loaded meshes are cached by URI with an LRU bounded by **both** entry count (32 max) and total vertex count (5M max) so a single pathological mesh can't keep three small ones from caching. Eviction disposes geometries and materials. **Per-consumer clones**: the cache holds the original parsed root and hands out `.clone(true)` copies because Three.js scene-graph nodes can't be parented to two scenes at once (each open 3D panel needs its own copy). Errors are caught at the dispatcher level and re-thrown as a single `MeshLoadError` carrying the URI, the file kind, and a friendly message; the robot subtree falls back to a small pink-wireframe placeholder at the visual's pose so a missing mesh doesn't leave the link invisible.
- **Robot subtree builder** (`src/components/panels/ThreeDScene/robotModel.ts`, ~340 LOC). Turns a parsed `UrdfModel` into a Three.js tree mirroring URDF semantics: per-link group anchored at the link frame, per-joint a two-group "origin pivot + axis group" pair, visuals attached to the link group with their per-visual origin transforms applied. URDF cylinders (axis-along-Z) get a fixed `rotateX(π/2)` baked into the geometry so the rendered orientation matches the spec without us needing to wrap each visual in another group. **Joint-state ingestion is a two-pass apply**: pass 1 copies raw `position[]` values into per-joint bindings (clamped to limits for `revolute` / `prismatic`, unclamped for `continuous` per spec); pass 2 re-applies `mimic` joints using the (now-populated) source positions, so a gripper mimicking its main joint resolves regardless of joint declaration order. Per-joint matrices are composed with `Quaternion.setFromAxisAngle(axis, value)` for revolute / continuous and `axis.clone().multiplyScalar(value)` for prismatic; the axis is normalised (with a `(1, 0, 0)` fallback when zero-length) so URDFs that emit `<axis xyz="0 0 0"/>` for fixed joints don't blow up. `renderOrder = -1` everywhere so opaque cloud points always draw on top of partially-transparent collada materials (matches RViz convention). The subtree is built once per (panel, model) and disposed in the panel's cleanup; mesh-load warnings surface in the modal's "Parser warnings" section after load.
- **`useJointStates` hook** (`src/hooks/useJointStates.ts`). Auto-detects the bag's `sensor_msgs/JointState` topic (type match first, then conventional `/joint_states` fallback), routes through the existing `useMessageAtTime` (which already collapses rapid playhead ticks onto the latest target), and returns a `Map<jointName, position>` plus a `hasTopic` flag the panel uses to show "no /joint_states - joints stay at rest" in the Display card when the bag doesn't publish one. Per-joint position extraction tolerates short `name[]` / `position[]` arrays so a partial state message doesn't kill the read; non-finite values are filtered.
- **Robot-model store** (`src/store/robotModelStore.ts`). A small Zustand store: `loaded: LoadedRobotModel | null`, plus per-panel `hiddenInPanel` flags. One URDF describes one robot; loading a new URDF replaces the previous model (and every open 3D panel rebuilds). The anchor link defaults to the URDF's first root link and the modal exposes a picker for the common case where the bag's TF tree uses `base_footprint` and the URDF declares `base_link` (or vice versa).
- **TF chain for the robot is computed independently from the data topic.** The panel's existing TF transform aligns the data topic's `header.frame_id` to the world frame; the robot's anchor link is rarely the same frame as the data topic. v1.3.0 adds a separate per-tick transform - `upFix * tfChain(anchorLink → worldFrame, playheadNs)` - cached by the same `(source, target, time)` key pattern the data-topic transform uses (~100 ms time buckets), so consecutive playhead ticks reuse the matrix without re-walking the chain. The robot root is parented to the panel's `worldGroup` so the up-axis fix is composed in for the rare bags from non-ROS-convention rigs (drone NED, camera-aligned LiDAR) where the user has flipped the up axis.
- **Bundled sample robot URDF**: `public/sample-bags/sample-robot.urdf` is a hand-written, mesh-free model (~3 KB) with `base_link` + 4 wheels (continuous joints) + a `sensor_mount` pillar + `laser` and `imu_link` children. The frame names match the bundled `tour.mcap` so a drag-and-drop of the sample robot animates correctly against the sample bag's `/tf` stream. Mesh-free by design: a fresh checkout serves the URDF without also needing to serve any package-resource directories. The modal's empty state has a "Try a sample robot" button that fetches this file directly.
- **20 new tests across two files**, **243 passing tests total** (was 223 at v1.2 with bag tests skipped on the 10 GB fixture). `tests/parsers/urdf.test.ts` (10 tests) covers primitive geometry (box / cylinder / sphere with origins, defaults), mesh parsing with scale defaults, missing-optional-origin tolerance, joint hierarchy walk with root discovery, malformed XML errors, xacro detection, named-material resolution at top level, dedup of unknown-element warnings (one `<gazebo>` warning regardless of how many `<gazebo>` blocks the URDF has, same for `<transmission>`), duplicate-link / duplicate-joint dedup, and the empty / non-`<robot>` error paths. `tests/parsers/packageResolver.test.ts` (10 tests) covers URL prefix persistence across "reloads" (via `vi.resetModules`), trailing-slash normalisation, object-URL minting from file bindings with a polyfilled `URL.createObjectURL` that captures the underlying Blob so the test can `.text()` it back, suffix / basename fallback for misaligned drop roots, binding clearing, every error path (missing mapping, malformed URI, `file://` rejection, missing file inside file binding), and pass-through for `http://` / `https://` URIs with extension extraction (case-insensitive, query-string aware).

Explicitly out of scope for v1.3.0 (each follows in a sub-version):
- **`MESH_RESOURCE` and `TRIANGLE_LIST` marker primitives** (v1.3.1) - the v0.8 pink-wireframe placeholder stays until v1.3.1 plumbs the same mesh loader into `markerObjects.ts`.
- **`CameraInfo` overlay + frustum** (v1.3.2) - independent of the URDF work, ships as its own PR.
- **Xacro evaluator**: ~1000 LOC of pure-JS XML transform, its own project. The modal explains the `xacro` pre-processing workaround when an unprocessed file is detected.
- **Mesh resolution from `package://` without a user-provided root** - no magic auto-resolve from URLs or GitHub. The alternative is fragile and a security risk. Users provide the package root once; persisted across sessions.
- **Image rectification from `CameraInfo`** - the v1.3.2 overlay will show intrinsics and the camera frustum, not rectify pixels. Real rectification needs a per-frame canvas remap with a model-specific (plumb-bob, fisheye, equidistant) implementation.

## v1.2: Cross-Format Bag Editing - ROS1 `.bag` + ROS2 `.db3` -> MCAP

Everything in v1.1, plus:

- **Bag editing now covers every format BAGEL reads.** v1.1 shipped MCAP-in / MCAP-out as the "first feature that replaces a CLI workflow rather than just visualises one." v1.2 closes the cross-format gap so the same `Edit` button - the same modal, the same trim + topic-filter UX, the same live message-count estimate, the same progress bar, the same `__edited.mcap` download flow - works regardless of whether the focused bag is `.mcap`, ROS1 `.bag`, or ROS2 `.db3`. Output is always indexed, chunked MCAP regardless of input, which keeps downstream tools (BAGEL itself, Foxglove Studio, the official `mcap` CLI, `mcap convert`) ingesting the result on the same path. The Toolbar's edit affordance no longer hides on `.bag` / `.db3` focus, and the modal's "v1.1 only supports MCAP" placeholder copy is gone for good.
- **ROS1 `.bag` -> MCAP** through a new `src/parsers/editRos1.ts` (~150 LOC). Reads through the existing cached `Bag` from `parsers/bag.ts:loadBag`, iterates `bag.messageIterator({ topics, start })` with a manual upper-bound time clamp inside the loop (the library accepts `start` but not `end`), and copies raw ROS1 wire-format bytes straight through with `messageEncoding: 'ros1'`. Schema text comes for free: each ROS1 connection's `messageDefinition` field already carries the concatenated `.msg` text with `=====` separators, which is exactly what MCAP's `ros2msg` / `ros1msg` schemas expect, so the registration is a single `writer.registerSchema({ name, encoding: 'ros1msg', data })` call per topic. Multi-publisher topics (multiple connections per topic name in the source bag) collapse into a single output channel since their schemas are identical - keeps downstream tools from rendering the same logical stream twice. Output header is tagged `library: bagel-edit/ros1` and `profile: ros1` so external tools can tell at a glance the bag came from a ROS1-side edit.
- **ROS2 `.db3` -> MCAP** through a new `src/parsers/editDb3.ts` (~200 LOC). The hard problem the other two formats don't have: `.db3` doesn't embed schemas. We resolve each surviving topic's type against the bundled `ros2galactic` registry plus any user-pasted custom schemas (the v0.8.1 paste flow), synthesise its `.msg` text on the fly via `@foxglove/rosmsg`'s built-in `stringify`, and register it as a `ros2msg` MCAP schema. Reading is a single SQL `SELECT topic_id, timestamp, data FROM messages WHERE timestamp BETWEEN ? AND ? AND topic_id IN (...) ORDER BY timestamp ASC` with the topic include set assembled against the `topics` table - sql.js yields naturally between `step()` calls so the progress callback can fire on the same 250-message cadence as the MCAP and ROS1 paths. Output header is tagged `library: bagel-edit/db3` and `profile: ros2`.
- **Missing-schema handling for `.db3` topics**: the bundled registry only covers the standard ROS2 packages (`std_msgs`, `geometry_msgs`, `sensor_msgs`, `nav_msgs`, `tf2_msgs`, `visualization_msgs`, `diagnostic_msgs`, `rcl_interfaces`, `rosgraph_msgs`, `builtin_interfaces`). Real-world `.db3` bags often carry vendor (`px4_msgs`, `autoware_msgs`) or in-house types that the registry doesn't know. v1.2's modal pre-flights this on mount via a new `getResolvableTopicsDb3` worker RPC: topics with no resolvable schema get a yellow `schema missing` chip in the topic row, are unchecked by default, and the user can opt them in to include the bytes anyway. Opted-in topics get a schema-less MCAP channel (`schemaId: 0`) - readable by tools that don't need schema text, including BAGEL itself once the user pastes a `.msg` for the type via the v0.8.1 flow. Topics not opted in are skipped with a one-time `console.warn` mentioning the topic name and type. This mirrors the v0.8.1 paste-flow ergonomics: users fix at the schema level once and re-edit, or accept a schemaless write.
- **Format-aware estimator path.** v1.1's `estimateMessageCount` read from `meta.reader.statistics` (MCAP-specific) to scale by the time-window fraction. v1.2 generalises through a new `estimateMessageCountForFormat(source, format, ...)` dispatcher: MCAP keeps the v1.1 path; `.bag` sums per-connection `count` over `bag.chunkInfos` and scales by the time-window fraction (same overshoot tradeoff); `.db3` runs a single SQL `SELECT COUNT(*)` - precise even on multi-GB bags because SQLite has the timestamp index. The modal calls the same `estimateEditCount` shim with the source's format and reads "~N messages" without caring which path served it.
- **Worker RPC surface.** Two new methods: `editBag(source, format, ...)` replaces v1.1's MCAP-only `editMcap` and dispatches through the new `editBag` in `parsers/edit.ts`; `getResolvableTopicsDb3(source)` powers the `.db3` schema pre-flight. The `estimateEditCount` RPC gains a `format` parameter. The progress callback contract is unchanged - every ~250 messages a `progress` message comes back through the same worker channel the streaming-decode methods already use. Result-transfer for the edited bytes still uses the zero-copy `[result.bytes.buffer]` transferable pattern from v1.1, so writing a 500 MB output costs one allocation in the worker and zero copies across the postMessage boundary regardless of input format.
- **Modal pre-flight + format-aware copy.** When the focused bag is `.db3`, the modal calls `getResolvableTopicsDb3` on mount, shows a one-line "Checking topic schemas against the registry..." hint while it's in flight, then narrows the default-included topic set to the resolvable subset. The header copy under "Edit bag" gains a format-specific paragraph: MCAP keeps its v1.1 wording, `.bag` explains the `ros1msg`/`ros1` schema flow, `.db3` explains the registry resolution + missing-schema chip. The filename default is `<bag-stem>__edited.mcap` regardless of input extension, since the output is always MCAP.
- **In-memory ROS1 bag writer for tests** (`tests/fixtures/synth.ts`). `@foxglove/rosbag` ships a reader but no writer, so the test fixture story for editRos1 needs its own bytes. The new `writeSyntheticRos1Bag(topics)` hand-rolls a v2.0-compliant bag from scratch following the reader's expectations in `node_modules/@foxglove/rosbag/dist/esm/record.js`: magic + bag-header record + one chunk (uncompressed) containing the connection + message_data records + per-connection index_data + index section (connection records + chunk_info). MD5 sums for connections come from `@foxglove/rosmsg`'s `md5(parseMessageDefinition(text, { ros2: false }))` helper. The writer doubles as an unblock for the previously-skipped synthetic ROS1 path in `bag.test.ts` (the existing comment noting "ready for a smaller one" finally has one). Quick-build helpers `chatterRos1Bag()` and `multiTopicRos1Bag()` parallel the existing MCAP `chatterBag()` / `multiTopicBag()`, with helpers `encodeRos1String` / `encodeRos1Int32` for the message payloads.
- **In-memory `.db3` writer for tests**: `writeSyntheticDb3(topics)` in the same `synth.ts` builds a `.db3` SQLite buffer via sql.js (the same WASM build the parser worker uses), inserts `topics` + `messages` rows matching the `rosbag2_storage_default_plugins` schema, and dumps to `Uint8Array` via `db.export()`. WASM path resolution uses `fileURLToPath(import.meta.url)` rather than `URL.pathname` because the latter returns `/C:/...` paths on Windows that Node's `fs` rejects. CDR-encoded message payloads come from the existing `MessageWriter` (`@foxglove/rosmsg2-serialization`) the MCAP synth path already uses, so `chatterDb3Bag()` and `multiTopicDb3Bag()` produce real round-trippable bytes without needing a separate encoder.
- **23 new tests across two files**, 6 ROS1 + 14 .db3 + 3 estimator/resolver coverage. Suite goes from 180 to 203 passing tests, wall time stays under 13 s. All new tests are synthetic-fixture driven (no disk hit), so a fresh CI checkout has everything the suite needs without downloading any new fixtures. The existing v1.1 `editMcap` tests are unchanged - the new dispatcher routes them through the same `editMcapBag` they always called, just one indirection deeper.

## v1.1: Bag Editing - Trim + Topic Filter + MCAP Export

Everything in v1.0, plus:

- **Browser-native bag editing**: an `Edit` button in the toolbar (visible whenever the focused bag is `.mcap`) opens a dedicated `BagEditModal` that trims the time range, drops unwanted topics, and downloads a fresh `.mcap` straight from the browser. The v1.1 banner feature, and the first time BAGEL replaces a CLI workflow (`mcap filter`, `rosbag2 convert`) rather than just visualizing what the CLI produced. The whole pipeline runs in the per-bag parser worker, so the React render loop stays responsive even while editing a multi-GB bag, and the result is streamed into an in-memory `Uint8Array` that's handed to the browser as a download Blob without ever touching disk on the server side (there is no server side). **Trim window**: two-handled mini-timeline plus numeric `Start (s)` / `End (s)` inputs that clamp against the bag duration; the modal computes the cut in bag-local seconds and converts to ns at submit time so the slider never carries BigInts and the user reads "0.00s to 30.00s" instead of `1_700_000_000_000_000_000`. **Topic filter**: every topic from the bag's summary renders as a checkbox row with name + type + message count; checked-by-default for topics with messages, an in-modal search field with `All`/`None`/`+ Visible` shortcuts when the list is long, and a final-state validation so submitting with zero topics surfaces an inline error rather than an empty output. **Live estimate**: a debounced `estimateEditCount` round-trip to the worker shows "~N messages, window 12.34s, X of Y topics" as the user drags the slider, so they don't have to start the actual edit to find out their cut is empty. Estimates use the `McapIndexedReader`'s statistics scaled by the time-window fraction, so they overshoot slightly when topics publish unevenly across the bag, which is good enough for a progress bar. **Progress bar during write**: every ~250 messages the worker posts a `progress` message back to the main thread; the modal renders a determinate bar (`written / ~estimated`) that finishes a hair early when the estimate over-counted, which is preferable to a wedged spinner that hides whether the edit is making progress. **Output format**: indexed, chunked MCAP with `useChunks` / `useStatistics` / `useChunkIndex` / `useMessageIndex` / `useSummaryOffsets` all on, so the output re-opens in BAGEL (or the official `mcap` CLI, or Foxglove Studio) with full range-read parity. Only the schema-encoding ID stays identical to the source so we don't accidentally invalidate panels that key on schema text. **Schema/channel re-use**: schemas and channels are registered into the output writer **lazily on first message** rather than up front, so editing a 30-topic bag down to 2 topics doesn't carry the 28 unused schemas in the output. Confirmed by a regression test that asserts `bytes.length(dropped /odom) < bytes.length(full)` on the `multiTopicBag` synth fixture.
- **Scope: MCAP input only, MCAP output only.** ROS1 `.bag` and ROS2 `.db3` inputs are explicitly out of scope for v1.1: `.bag` would need ROS1-encoding round-tripping (`ros1msg` schemas + `ros1` message encoding into MCAP), and `.db3` would need schema reconstruction from the bundled type registry (since `.db3` doesn't embed schemas). Each is its own pass of work and earmarked for v1.2. The modal explicitly tells the user this when the focused bag is `.bag` / `.db3`, with a "convert via `mcap convert` and re-open here" workaround, rather than dangling a non-functional button. Output is always uncompressed MCAP for the same reason that v0.7+ MCAP support uses `fzstd`: the library is decompress-only, we don't have a pure-JS zstd *encoder* yet. Output bags reload identically; only their on-disk size differs from a zstd-compressed equivalent (typically 2-4x larger). Adding zstd output is a v1.2 polish item once a sensible encoder lands.
- **Filename UX**: default output name is `<bag-stem>__edited.mcap` (double underscore matches the export filenames the v0.5 CSV/NDJSON exporters use, so an editor that keeps `tour__odom.csv` and `tour__edited.mcap` in the same folder sorts them next to each other). Users can edit the field freely; the writer strips path separators and re-adds the `.mcap` extension if missing so the OS file picker treats the result as MCAP. **Filename sanitisation** runs at submit time, not on every keystroke, so a user mid-typing doesn't see characters disappear.
- **Library string**: output MCAPs are tagged `library: bagel-edit/<source-library>` in their header, so downstream tools (and `mcap info`) can tell at a glance that a bag came out of BAGEL's editor rather than a recorder. The source library is preserved as a suffix so the bag's provenance still reads in the header.
- **Test coverage**: 12 new tests in `tests/parsers/edit.test.ts` covering the time-range filter (chatterBag with `[1.5s, 2.5s]` keeps 1 message and the value decodes correctly), the topic filter (multiTopicBag with `topics: ['/odom']` removes /chatter), the empty-include-list edge case (`topics: []` produces an empty bag that still parses cleanly), the schema-pruning regression (smaller output when topics are dropped), the progress callback cadence (>250 messages triggers at least 2 ticks plus tail), the empty-window error path, the round-trip-decode invariant (edit then re-parse then decode then assert values match), the custom-profile passthrough, and three real-bag integration tests against `public/sample-bags/tour.mcap` (mid-bag 5s trim yields a ~3-6s duration; `topics: ['/odom']` leaves only `/odom` in the edited topic list with 200-400 messages out of ~300 expected; multi-topic subset preserves schema names). **180 passing tests total** (was 168 at v1.0), still under 12 seconds wall time locally.
- **Worker plumbing**: two new RPC methods on the parser worker (`estimateEditCount`, `editMcap`) plus a small `loadMcapForEdit` re-export from `parsers/mcap.ts` that exposes just the cached `McapIndexedReader` without leaking the rest of the internal cache shape into `parsers/edit.ts`. The transferable-buffer optimization from the v0.4 PointCloud2 path applies here too: the output `Uint8Array.buffer` is shipped back to the main thread zero-copy, so writing a 500 MB bag costs one allocation in the worker and zero copies across the postMessage boundary.

## v0.6: ROS1 `.bag` Support

Everything in v0.5, plus:

- **Responsive toolbar**: the full stats row collapses to a compact `duration · msgs · topics` strip on tablet-width viewports and stacks below 900 px so portrait iPads no longer push the close button off-screen.

## v0.4: 3D Visualization

Everything in v0.3, plus:

- **ThreeDScene panel**: a Three.js-powered 3D viewer that opens on `sensor_msgs/PointCloud2`, `sensor_msgs/LaserScan`, and pose-bearing topics (`Odometry`, `PoseStamped`, `PoseWithCovarianceStamped`, `TransformStamped`). Orbit controls (drag to rotate, wheel to zoom, right-drag to pan) with damping; ROS Z-up convention so "up" actually points up. A faint ground grid in the XY plane and a world-axis triad keep the user oriented at all zoom levels.
- **PointCloud2 rendering**: decodes the packed binary layout from each message's `fields` array which supports `FLOAT32 / FLOAT64 / INT8…INT32 / UINT8…UINT32` datatypes, the RGB-packed-in-a-float ROS convention, and intensity / ring fields. Colormaps: **height** (z), **intensity** (or ring index if no intensity), and **single colour**. Sub-samples to 250k points per frame so a full 1 M-point sweep doesn't lock the page; reuses GPU buffers across playhead ticks when the point count is stable. A FLOAT32 fast path reads x/y/z through a typed-array view (no DataView dispatch) for typical Velodyne / Ouster / RealSense streams.
- **Livox CustomMsg support**: list-of-struct point clouds (`livox_ros_driver2/msg/CustomMsg` and similar) share the same render pipeline which gets detected by shape, not by hard-coded type name, so converted bags with non-standard package names still work.
- **LaserScan overlay**: lifts the polar `(range, angle)` ring into 3D at `z=0` so it sits naturally on top of the ground grid. Coloured by distance from the sensor (Turbo colormap) so depth is visible at a glance.
- **Pose / Odometry markers**: rendered as a coordinate-frame axes triad with a forward-pointing arrow, oriented by the message's quaternion. Track a robot's pose through the scene in real time as the playhead advances.
- **TF-aware rendering**: when the bag has `/tf` and `/tf_static`, every panel composes the chain from the source topic's `header.frame_id` up to a chosen *world frame* (`map` or `odom` by default) and applies it to the rendered geometry. A dropdown in the panel's Display card lets you switch the world frame at any time. Without TF, panels render directly in the topic's local frame and surface that fact.
- **Custom orbit pivot**: `Shift+Click` anywhere in the 3D viewport sets the orbit centre to that scene point. Raycasts the live cloud (and the accumulator) with a pick threshold tied to the camera view radius, falls back to the `z=0` ground plane when nothing is hit. A wireframe sphere marks the chosen pivot; a `Reset pivot` button reverts to the auto-fit centre without disturbing the camera angle. Solves the case where the cloud isn't centred on its sensor origin and orbit feels off-axis.
- **Range filter**: a `limit range` slider (1–200 m) in the Display card drops returns farther than the cap before bounds + height-colour stats are computed. Recovers useful height colouring on long-range Velodyne / Ouster scans where a handful of 100 m returns would otherwise compress the colormap into a thin slab.
- **Point accumulation**: a ring-buffer mode that builds up a running "map" view from many frames (drone flights, SLAM runs, vehicle traversals). New frames are sub-sampled (`per-frame pts`, 1k–500k) and appended in world frame via the cached source→world TF matrix; oldest points drop FIFO once the budget (0.25M–10M) is hit. Auto-clears on topic / world-frame / up-axis change, and warns when no `/tf` is present (frames will overlap in the sensor frame). Voxel-grid downsampling for "build a 60-second field map" workflows is slated for v0.5.
- **Custom up-axis**: a 6-option selector (`±X / ±Y / ±Z up`) handles bags whose clouds aren't ROS-standard Z-up for upside-down PCDs, drone NED frames, camera-aligned LiDAR rigs. Applied as a pre-multiplication on the TF chain so it composes for free with the existing graph; no decoder changes.
- **Display controls**: per-panel pop-out card with color-mode buttons (PointCloud2), point-size slider, range filter, accumulation controls, grid / axes toggles, up-axis selector, and the world-frame selector.
- **3D quick-button**: `PointCloud2` and `LaserScan` topics expose a `3D` button in the sidebar and default-open the 3D panel on click. Pose-bearing topics gain a `3D` option alongside their existing `Path` and `Plot` buttons.

## v0.3: Trajectory, TF Tree & Web Worker

Everything in v0.2, plus:

- **TrajectoryPlot** panel: click any pose-bearing topic to render its 2D path. Supports `nav_msgs/Odometry`, `geometry_msgs/PoseStamped`, `PoseWithCovarianceStamped`, `Pose`, `Point(Stamped)`, `TransformStamped`, and `sensor_msgs/NavSatFix` (equirectangular projection from the first GPS fix). The polyline runs blue → red along the path, with a playhead marker that follows the bag time and a heading arrow when the source message has an orientation quaternion. Mouse-wheel zoom, drag-to-pan, and a dynamic scale bar in metres / km.
- **TFTree** panel: parses `/tf` and `/tf_static` into a single graph and renders the frame hierarchy as an interactive top-down tree. Click any frame to see its current transform (translation, quaternion, Euler angles in degrees) at the playhead time, and to highlight the root → frame chain. Static and dynamic edges are visually distinct (dashed vs solid).
- **Web Worker parsing**: every heavy operation like initial bag parse, MCAP chunk zstd-decompression, sql.js queries, CDR deserialization which now runs in a dedicated parser worker. The React render loop stays responsive while a topic decodes; scrubbing the timeline, toggling panels, and resizing the layout no longer block on the bag. `@mcap/core`, `sql.js`, `fzstd`, and the `@foxglove/*` libraries live entirely in the worker chunk and never touch the UI thread.
- **Smarter sidebar panel buttons**: each topic row now offers exactly the panel kinds that fit its type. Pose topics get a `Path` button, `/tf` and `/tf_static` get a `TF` button, image topics keep `Image`, and `Raw` is always available. The default-click panel matches the topic's nature (TF → tf, pose-only → trajectory, image → image, otherwise → plot).

## v0.2: Plotting, Image Viewer & Playhead

- **Global playhead**: timeline strip at the bottom with click/drag scrub, play/pause, 0.25×–4× speed, and Spacebar shortcut. Every open panel syncs to the same timestamp.
- **TimeSeriesPlot** panel: click any non-image topic to chart its numeric fields. Auto-extracts every numeric leaf (e.g. `linear.x`, `angular.z`, `orientation.w`) as a separate series, with per-field visibility toggles. uPlot-driven, handles up to 50,000 points per panel.

- **RawMessageInspector** panel: collapsible JSON tree of the deserialized message at the playhead, with type-aware coloring and hex dumps for `Uint8Array` fields.
- **Resizable panel layout**: sidebar and visualization panels are split by `react-resizable-panels` handles; drag to reflow.
- **Active-panel indicator**: small blue dot on sidebar topic rows that already have a panel open.
- **Zstd-compressed MCAP support**: bags recorded with `--compression zstd` (the new ROS2 default) decompress via a pure-JS zstd decoder, no extra setup.
- **Multi-GB file handling**: MCAP indexed reader does range reads against the source `File` instead of loading the whole bag into a single ArrayBuffer; bags well over 2 GB work.
